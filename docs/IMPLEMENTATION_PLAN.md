# 求职面试 Agent 对话式改造实施计划

版本：0.2　日期：2026-09-30　依据：[PRD](./PRD.md)

## 1. 现状与改造目标

项目已有 React + Vite 聊天页、Express、SSE、Zustand、Zod、OpenAI 兼容模型网关、文档解析、配置型 Skill、服务端面试轮次、JD 匹配运行记录及受控 MCP 搜索适配。此前扩展出的资料操作区和独立结果入口需要收回到聊天流；保留现有侧栏、消息气泡、输入区和 CSS 风格。

本轮交付是**本地对话式产品**：`POST /api/chat` 作为统一入口，每条用户消息都调用 LLM 意图识别，在同一会话内动态选择求职会话、面试、匹配、背调或自定义 Skill；上传/粘贴资料、模型切换和结果追问都留在聊天页。登录和服务端完整会话历史属于公开版门槛，不把当前固定 `ownerId=local` 当作多用户能力。

## 2. 目标调用链

```text
React 聊天页：消息 + 当前模型 + 关联文档 ID + 可选显式 Skill
  → POST /api/chat（SSE，requestId/sessionId）
    → LLM 意图路由：当前消息 + 最近对话 + 活跃任务 → intent/skill/任务参数
      → 服务端会话状态：校验 Skill、补齐缺失输入、决定当前动作
      → 当前 Skill 运行器：求职会话 / 面试 / JD 匹配 / 公司背调 / 用户 Skill
        → 按轮组装上下文 → 模型网关或服务端批准的 MCP 工具
    → status/delta/result/done/error 返回同一消息流
```

路由调用和实际生成调用可用不同模型。`AI_ROUTER_MODEL_ID` 是可选的服务端模型 ID；未设置时使用本轮选中的模型或默认模型。用户在会话中切换生成模型，从下一条消息生效；当前面试阶段和已关联资料保持不变。路由失败返回可重试错误，不用关键词规则暗中执行另一个 Skill。

## 3. 模块与状态边界

| 模块 | 本轮职责 | 后续升级口 |
| --- | --- | --- |
| `server/routes/chat.ts` | 保留 SSE 契约，校验请求、调用意图路由并分派 Skill | 公共会话 API 接管历史与幂等 |
| `server/llm/` | 根据 `modelId` 调用 OpenAI 兼容端点；结构化路由/结果验证 | 增加独立协议及模型能力检测 |
| `server/skills/` | 内置求职会话与三个专项 Skill；设置中的自定义配置与版本 | 自定义 Skill 绑定 owner、审核工具白名单 |
| `server/interviews/` | 继续管理面试时间、题目、回答、追问和复盘 | 与服务端对话事务关联 |
| `server/documents/` | 上传原件、解析文本和来源块；粘贴文本包装 `.txt` 复用上传接口 | OCR、对象存储、更多格式 |
| `server/skill-runs/`、`server/mcp/` | 匹配/背调运行和受控搜索；结果回写聊天消息 | 运行记录的用户隔离及真实 MCP 质量评估 |
| `src/` | 保留聊天视觉；输入区附件、消息内报告、模型选择、设置中的 Skill 管理 | 微信小程序客户端复用后端 API |

**状态所有权：** 本地版普通聊天仍由浏览器保存，服务端已经保存面试与分析任务。每个消息结果应记录 Skill ID/版本、模型 ID 和材料 ID；内部运行记录可用于恢复和审计，用户看到的完成结果留在原会话消息里，不另设“历史结果”列表。公开版再把完整会话、消息、附件关联和路由决定迁到服务端。

原“定向简历草稿”来自用户最初要求“针对 JD 生成新的简历”。目标体验是聊天中返回一份**可继续要求修改的文稿**，标出所依据的原始经历和待核验内容；它不是独立工作台页面，也不应自动写回原简历。

## 4. 本轮 API 合同

| 方法 | 路径 | 当前/本轮用途 |
| --- | --- | --- |
| `POST` | `/api/chat` | SSE 聊天主入口；`requestId`、`sessionId`、`messages` 必填，可带 `modelId`、`skillId`、`jdDocumentId`、`resumeDocumentId`、面试参数或公司名 |
| `GET` | `/api/models` | 展示可选模型及能力；用户选择的 `modelId` 用于本轮生成 |
| `POST` | `/api/documents` | `multipart/form-data`，`kind=jd|resume` 与 `file`；粘贴文本在前端包装为 UTF-8 `.txt` 上传 |
| `GET` | `/api/documents/:id` | 文档原文与解析状态预览；`needs_ocr` 不进入模型 |
| `GET/POST/PUT/DELETE` | `/api/skills`、`/api/skills/:id` | 设置页读取、创建、编辑、删除配置型 Skill |
| `POST/GET` | `/api/interviews` 等 | 本地版保留的面试内部接口，由聊天入口编排，不提供独立产品页 |
| `POST/GET` | `/api/skill-runs` 等 | 本地版保留的分析内部接口，结果嵌入聊天消息 |

SSE 保留 `delta/done/error`，增补 `status/route/result` 等事件时前端应兼容未知事件。写入请求以 `requestId` 去重；面试回答继续使用已有去重规则。当前聊天接口仍由浏览器发送有限历史，服务器须限制条数和总字数。`POST /api/conversations/:id/messages` 是公开版服务端会话迁移目标，**不是本轮已实现接口**。

## 5. 本轮落地顺序与验收

### A. 意图路由与 Skill 分派

1. 加入普通求职会话内置 Skill；定义结构化路由结果 `intent`、可选 `skillId` 与任务参数，输入包括当前消息、近期上下文、活跃面试和关联材料。缺失输入由服务端按任务状态判断。
2. 每条消息运行路由；显式 Skill 选择作为提示而非让客户端指定未授权工具。只将被选中 Skill 的阶段与提示词传给生成模型。
3. 将已有面试、匹配、背调服务适配为聊天调用。缺 JD/简历/公司名时在对话中追问；扫描 PDF 或无来源时显示明确状态。面试的下一题与报告在同一消息流呈现。
4. 路由模型通过可选 `AI_ROUTER_MODEL_ID` 配置，必须指向已配置且支持结构化输出的模型；选项无效时服务启动或请求给明确错误。

**验收：** 使用同一段聊天先问普通问题，再说“按这份 JD 面试我”，回答一题后请求背调；每条消息均经过 LLM 路由，结果留在聊天中，没有打开独立工作台。

### B. 聊天 UI 与资料

1. 沿用现有视觉，把文件上传、粘贴材料、模型选择和结果交互放在输入区/消息区；侧栏只保留会话历史。设置内管理自定义 Skill，不在首页陈列多个任务入口。
2. 上传 PDF/DOCX/TXT/MD 复用 `/api/documents`；粘贴文本包装 UTF-8 `.txt`，用户确认它是 JD 还是简历，得到文档 ID 后关联当前会话。解析预览可见；上传失败不改变当前关联。
3. 模型选择在会话中可随时改；本轮消息使用发送时选定的模型，并在消息元数据保留模型信息。定向简历作为可复制、可继续修改的聊天文稿显示。

**验收：** 上传和粘贴都能进入后续面试/匹配；切换两个模型后后续响应来自新模型；窄屏仍能发消息、查看附件与来源。

### C. 本地验证

- 用无需真实付费模型的假网关覆盖四类路由、进行中面试的回答/结束、缺输入追问、模型切换和路由失败。
- 用技术岗及非技术岗中文 JD 验证问题与要求相关；检查简历文稿不虚构、背调无 URL 时不产生事实。
- 运行 `npm run build`、`npm run lint` 与现有离线测试。真实模型和 MCP 搜索服务需单独做手工端到端验收，不把假服务结果写成线上质量结论。

## 6. 公开 Web 版与小程序顺序

1. **服务端会话：** 新建 `Conversation/Message/Attachment/SkillRun` 数据契约，持久化每轮路由、模型、来源与结果；历史不再依赖浏览器整包回传。新增会话列表、读取、发送、删除接口，旧 `/api/chat` 迁移时保留兼容窗口。
2. **认证与隔离：** 接入托管认证，从会话取得 `ownerId`，所有文档、Skill、面试和运行记录读写都按 owner 校验；双账号自动测试。补限额、删除、备份、上传扫描和日志脱敏后才允许公开部署。
3. **资料与结果质量：** OCR、常用格式扩展、修改对照和事实核验、DOCX/PDF 导出；真实 MCP 搜索验证公司消歧、来源时效和失败处理。
4. **微信小程序：** 复用同一 Express 会话和 Skill API，单独实现小程序认证适配与聊天 UI；模型密钥、路由和 MCP 不进入客户端。先完成 Web 服务端状态与权限，再接第二客户端。

Node 24 `node:sqlite` 适合本地单实例；公开版需持久存储、备份与恢复，扩展到多实例时再迁 Postgres。无需先引入完整 Agent 框架或向量数据库。

## 7. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 意图识别误判或模型不可用 | 结构化校验、用户可见的路由状态与澄清；失败可重试，不偷偷换任务 |
| 长对话超出上下文预算 | 只取任务相关资料、近期轮次和摘要；完整记录存储，后续补摘要质量检查 |
| 用户材料、网页或 Skill 提示词注入 | 平台规则保持高优先级；工具目标仅由服务端配置，自定义 Skill 不执行代码 |
| 简历改写形成虚构经历 | 将原始事实、推断、改写稿分层；待审核文稿逐条标记来源或待确认 |
| MCP 搜索无来源或服务失败 | 无有效 URL 不让模型生成公司事实；返回明确错误或“未查到” |
| 本地数据被误当作多用户系统 | README 和 UI 标明本地版；认证、隔离、限额、删除与备份全部通过后才公开发布 |
